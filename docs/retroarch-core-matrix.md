# RetroArch Core Matrix

This is the human-readable checklist for console iteration work. The app source of truth remains `data/emulators/cores.json`; the TUI and backend readiness panels read from that registry for core and BIOS checks.

Special runtime notes:

- Nintendo DSi: see [nintendo-dsi-runtime.md](nintendo-dsi-runtime.md).

When completing a console, update both places:

- `data/emulators/cores.json`: core IDs, BIOS IDs, optional BIOS IDs, and notes.
- `backend/data/console_progress.json`: provider/readiness/runtime validation status and notes.

## Runtime Contract

Every console we mark as ready must have enough machine-readable metadata for a fresh TUI install to reproduce the same result without manual rediscovery:

- Backend assignment exposes the console module, master ROM list, provider entries, and provider cache metadata to the client.
- Provider entries identify the runtime family when it matters, such as `fbneo`, `mame_current`, `mame_legacy`, direct CHD, extracted archive member, or MAME softlist.
- `data/emulators/cores.json` maps the console GUID to the preferred core, fallback cores, required BIOS files, optional BIOS files, and any core-specific notes.
- BIOS requirements include the expected RetroArch `system` relative path, checksum when known, and source metadata when we have a user-opt-in source.
- The TUI must select only providers compatible with the active frontend/core profile. Coverage-only providers should stay visible for administration but must not be treated as ready-to-play downloads.
- The installer must know whether to keep ZIPs intact, extract a ROM member, generate `.m3u`, generate a MAME command file, or install CHD/CUE/BIN content directly.
- Runtime validation notes must include at least one smoke-tested ROM/provider/core/frontend combination, including special launch options when needed.
- Disk-space preflight must happen before queueing downloads, using provider download size when available and preserving a minimum free-space reserve.
- Removing access to a console must create a cleanup decision for the user; local ROMs/playlists are not silently deleted.

If any of these are missing, the console should be treated as `backend_ready` or `needs_backend_work`, not fully `runtime_validated`.

## Status Meanings

| Status | Meaning |
| --- | --- |
| `runtime_validated` | Provider, install, playlist, core, and at least one ROM launch were confirmed. |
| `backend_ready` | Backend/provider/RDB metadata is prepared, but runtime validation is not complete. |
| `needs_backend_work` | Missing provider, RDB, core, BIOS, or coverage metadata. |
